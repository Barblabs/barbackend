# CMDB Providers sit behind a snapshot interface; Postgres does not

Every CMDB Provider is an adapter under `internal/cmdb/<provider>` implementing `ParseSettings`, which validates a CMDB Source's connection settings and its decrypted credentials (ADR 0012) without I/O and returns them parsed. Only parsed settings can `Snapshot`, which returns every in-scope record of the source as imported values plus its Skipped Records, or an error if it could not read them all, so no Sync can read a CMDB Provider with settings that were never validated. Parsed settings can also `CheckCredentials`: one cheap authenticated call that succeeds or returns a provider-agnostic `cmdb.Failure` with a stable code (`unreachable`, `tls_error`, `invalid_credentials`, `unexpected_response`, or a provider-specific one such as iTop's `missing_rest_profile`) and a readable message, so the dashboard can test a login and translate why it failed. `FromLogin` builds a source's settings and credentials from the URL, user and password an admin types, so the HTTP API takes the same login for every provider. Adapters also implement `Describe`, which reads the URL and user that identify a source to a person from its plain settings alone, so showing a source never opens its credentials. Settings are parsed when the source is added, so a typo fails then rather than at its first Sync, and again before each Sync, so settings that a newer adapter no longer accepts fail with a clear error. Authentication, pagination, provider classes and normalization of external formats stay inside the adapter, and each adapter parses its own connection settings, stored as an opaque JSON document on the CMDB Source. The snapshot types (`Snapshot`, `Record`, `SkippedRecord`) live in `inventory`, not `cmdb`, because the pure reconciliation rules (ADR 0005) consume them and the domain cannot import its adapters. The Sync (`sources.Service.Sync`) reconciles a snapshot with the stored Assets using those rules, so a complete snapshot is what allows an Asset missing from the source to be marked Inactive. `internal/cmdb` holds only the seam and the Sync lives in the use-case package `internal/sources`, so adapters depend on `cmdb` and `inventory` but never on Postgres.

The seam is real: a test fake implements it today, and iTop and ServiceNow are next. Postgres has no interface: it has a single adapter and tests run it for real, one fresh database per test cloned from a migrated template, so a port would be indirection without a second implementation.

## Considered Options

- **Incremental change feeds**: rejected; deletions are invisible to them, and providers expose changes very differently.
- **A repository interface over Postgres with an in-memory fake**: rejected; the bugs worth catching here (constraints, transactions, row locks) would only exist in the real database.
